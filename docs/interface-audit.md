# Interface audit · 13 October 2026

The review covers the existing Polli interface, navigation, accessibility, responsive layout, loading and error states, recipe editing, account review, planning, shopping, and offline controls. Verified defects were fixed in the application, with regression checks added for the affected flows.

Appearance choices were also excluded from the dropdown’s arrow-key navigation. They now use radio menu items that participate in the normal menu navigation and announce their selected state.

Screenshot review also corrected a narrow step-category column, duplicate recipe-tag pill styling, and curved day-heading borders. Weekly meal rows now align across days using shared grid tracks, while retaining complete recipe notes. Regression checks verify readable category widths and matching meal-row positions.

## Scope and evidence

The browser matrix covers the home/search screen, recipe, editor, cookbook, feed, planner, shopping list, account dialog, and preview index. It checks 320px light, 390px dark, 768px light, and 1280px dark layouts: 36 screen/viewport combinations. Each check verifies the heading, theme, page width, mobile labels where applicable, and axe accessibility rules. The narrow and desktop cases also save full-page screenshots under `test-results` for visual review.

Behavioral coverage includes blocked storage, unavailable UUID APIs, cancelled navigation, modifier clicks, keyboard focus, destructive confirmation, persistent Undo, failed-request retries, signed-out cookbook access, partial time labels, readable assistant suggestions, and empty/setup screens. The existing browser suite additionally exercises recipe validation, draft saving, publication, publication recovery, appearance preferences, and persisted planner selection and notes through the local HTTP fixture.

The shared T3 preview was used for browser inspection and initial accessibility measurements. Its screenshot host was intermittently unavailable; the repository's browser tests provide the screenshot evidence. API tests use the isolated in-memory fixture and synthetic account, with no real account or database writes.

## Remaining improvements and limits

1. **Initial loading performance:** the client still has a single application bundle above Vite's 500kB warning threshold. Loading editor, planner, and account modules on demand is the next performance improvement. This audit does not claim a production performance score.
2. **Assistive technology:** automated rules and keyboard checks do not substitute for a complete VoiceOver/NVDA reading test. Recipe announcements, calendar navigation, and nested account confirmations merit a dedicated screen-reader session.
3. **Real devices and browsers:** resized Chromium views cover layout breakpoints. Safari/WebKit, Android installation, safe areas, on-screen keyboards, native sharing, clipboard permissions, and offline updates need device checks before release.
4. **Live services:** real OAuth, provider-hosted photos, production network latency, and cross-device shopping updates require a deployment and real accounts. The fixture validates application behavior without proving those integrations.
